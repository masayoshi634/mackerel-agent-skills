# 検出パターンと確認手順

`scripts/trace.sh` が 1 トレースから機械的に出す `findings[].type` と、`scripts/triage.sh` がログの集計から拾う `inconsistency_detected`。
triage.sh はこれを複数トレースにまたがって集計し、`hypotheses[]`（`cause.direct` / `cause.structural` 付き）にする。
エージェントはこの表の「確定のための確認」で裏取りし、「コードで探すもの」を `references/code-inspection.md` の手順で `file:line` に落として、報告の「原因」と「恒久対策（原因箇所付き）」を書く。

| type | 検出条件 | 直接原因（何が起きたか） | 構造的な原因（なぜ失敗・不整合になるか） | 確定のための確認 | コードで探すもの | 止血 | 恒久対策 |
|---|---|---|---|---|---|---|---|
| `client_error_server_ok` | 呼び出し側の client span が `error` なのに、同じ時間帯の呼ばれた側の server span は `error` でない（HTTP 2xx）。`server_finished_after_client` が true なら呼ばれた側は呼び出し側が諦めた後に完了 | 呼ばれた側の応答時間が呼び出し側のタイムアウトを超えた | 呼ばれた側が「結果を確定してから応答する」順序のため、タイムアウト後に結果が片方にだけ残る。呼び出し側のタイムアウトが呼ばれた側の処理時間（p99）より短い | 呼ばれた側のログで同じ業務キー（`*.id` / `*_ref`）の完了ログを探す。照合ログやゲージ（`orphan` / `inconsistency` / `stale`）の件数を見る | 呼び出し側のタイムアウト設定とリトライ、呼ばれた側で結果を確定する行と応答を返す行の順序、タイムアウト時に呼び出し側が何を記録するか | 呼ばれた側の遅延原因（直近のデプロイ・設定変更、依存先、リソース、負荷）を特定して止める。復旧手段（照合 API、管理コマンド）があれば原因を止めた後に実行する | 業務キーを冪等キーにして再送と照合を安全にする。結果不明の失敗を補償処理か照合バッチで回収する。呼び出し側のタイムアウトを呼ばれた側の p99 より長くするか、処理を短くする |
| `server_5xx` | HTTP 5xx を返した server span。`depth` が最大のものが起点の候補 | 起点サービスがエラーを返した（`failure_reason` / ログ本文がその理由） | 依存先の失敗や設定不備が、上流に 5xx として伝播している | 起点サービスの ERROR/WARN ログ本文、`failure_reason` の値、直近のデプロイ・設定変更 | `failure_reason` やエラー文字列を返す分岐、そのルートのハンドラ、依存先を呼ぶ行 | 起点サービスの直近の変更（デプロイ・設定・依存先）を特定して戻す | 上流でのリトライ / フォールバック、起点サービスのエラー予算の監視 |
| `db_error` | `db.system.name` を持つ client span が `error` | DB 操作の失敗（`status.message`） | 接続プールの枯渇、ロック競合、スキーマ不一致、クエリのタイムアウト未設定 | `status.message`、DB 側の接続数・ロック・ディスク | 接続プールの設定、クエリのタイムアウト、該当クエリを発行する行 | DB 側の原因を取り除く（接続の解放、ロックの解消、容量） | 接続プールとタイムアウトの設定、リトライ |
| `server_4xx` | HTTP 4xx の server span（情報） | 業務上の拒否（在庫不足、バリデーション） | 急増していれば上流の入力やバージョン不一致 | 件数が急増していなければ正常 | バリデーションの分岐 | 通常は不要 | クライアント側の修正 |
| `inconsistency_detected` | WARN/ERROR ログの本文が `reconcile` / `inconsisten` / `orphan` / `drift` / `mismatch` / `stale` に一致し件数を報告している | 照合ジョブが「壊れた状態」を検出した（アラートの値がその件数） | 上の `client_error_server_ok` などで結果が片方にだけ残った | 照合 API / 管理コマンドで一覧を取る | 照合ジョブの実装、復旧の API やコマンド（`admin` ルート、Makefile のターゲット） | 原因を止めた後に復旧手段を実行する。猶予時間があれば時間をおいて再実行する | 失敗時の補償処理を自動化する |
| （パターンなし） | status も HTTP も正常 | 遅延かトラフィック量 | - | `slow_routes` の p95、ダッシュボードの Requests / p99 の推移 | 遅いルートのハンドラ、N+1、外部呼び出し | スケール、キャッシュ | 遅いルートの設計見直し |

## 仮説を組み立てるときの順番

1. **一番深い（末端の）異常を探す。** 上流の 5xx は結果。`findings` の `depth` が大きいもの、`client_error_server_ok` の `to` 側が起点。
2. **同じ traceId のログで裏取りする。** トレースは「どこで・どれくらい」、ログは「なぜ」。`failure_reason` や `error` 属性、`detail` を読む。
3. **広がりを数える。** `services[].error_routes` の件数と率、`log_groups` の件数。「全部失敗」か「3 割」かで対処が変わる。
4. **結果不明の失敗を疑う。** タイムアウト（`context deadline exceeded`、`ETIMEDOUT`、`Client.Timeout`）は「失敗したかどうか分からない」失敗。呼ばれた側に結果が残っていないかを必ず確認する。
5. **アラートの値の意味を確認する。** `[... 5xx errors]` は件数、`[... p99 latency]` は ms、ゲージの監視（不整合の件数など）は「今壊れている件数」。ゲージは原因を止めても **復旧操作をしないと下がらない**。
6. **直接原因と構造的な原因を分けて書く。** 直接原因は「今回何が起きたか」（遅延、エラー、設定）、構造的な原因は「なぜそれが失敗や不整合になるか」（順序、タイムアウトの不整合、補償処理の不在）。止血は直接原因に、恒久対策は構造的な原因に対応づける。
