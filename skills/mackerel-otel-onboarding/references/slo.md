# SLO の提案（フェーズ 4.5）

「エラーが 50 件で CRITICAL」のような既定値は、なぜその値なのかをユーザーに説明できない。
代わりに **サービスの役割とコードのタイムアウト、実測から目標（SLO）を導き、それをしきい値に翻訳する**。
全サービス分をあなたが埋めてから提示し、ユーザーには 1 問だけ答えてもらう。

## Mackerel でできること（先に押さえる）

- query 監視は **しきい値型**。「30 日で 99.9%」「バーンレート」は監視できない
- PromQL の **ベクトル除算が無い** ので、エラー率(%)は監視式にできない。5xx の **件数 / 5 分** に翻訳する
- APM の統計 API が返すレイテンシは **p95 まで**（`approxP95Millis`）。p99 の実測は無いので、目安は p95 × 1.5 程度
- だからこのフェーズの成果物は「合意した目標」と「件数と ms に翻訳したしきい値」と「翻訳の根拠」。根拠は監視ルールの memo に残り、Mackerel の画面と `report.sh` で読める

## 1. 役割の判定

discover の `ports` / `depends_on` / `upstream_env` と、コードのルート一覧から決める。迷う境界例はユーザーに確認する。

| 役割 | 判定 | 例 |
|---|---|---|
| `entry` | ホストに公開ポートがあり、compose 内の他サービスから呼ばれない | Web フロント、BFF、公開 API |
| `internal` | compose 内の他サービスの `*_URL` に自分の名前が出る | 商品 API、カート API |
| `gateway` | 自分の `*_URL` / `*_HOST` が compose 内のサービス名でない（外部サービスを呼ぶ） | 決済、メール送信、外部 API のラッパー |
| `worker` | HTTP ルートが無い、または定期処理・キュー消費だけ | バッチ、reconciler、コンシューマ |

開発用に公開ポートを全サービスに付けているアプリでは、公開ポートより「他サービスから呼ばれているか」を優先する。

`*_URL` が無くても **決済・メール・SMS・通知・外部 API の名前を持つサービスや、外部サービスのモック / スタブは `gateway` とみなす**。
本番では外部を呼ぶ前提で設計されているので、可用性を自分で約束できず、タイムアウト（結果不明）を数える監視が要るのは同じ。
規則で `internal` になるが名前や実装から外部相当と読めるサービスは、提案表に「規則上は internal、外部相当のため gateway として提案」と書いて承認の 1 問で確認する。
`worker` は RED のルールを作らない（`create-monitors.sh --services` から外す）。代わりに不変条件のゲージ（`references/business-metrics.md`）で監視する。

## 2. 呼び出し側のタイムアウトとリトライを拾う

呼ばれる側のレイテンシ目標は、呼び出し元が待てる時間で決まる。コードを grep して「誰が何秒で諦めるか」を表にする。

| 言語 | 探すもの |
|---|---|
| Go | `http.Client{Timeout:`、`context.WithTimeout(`、`http.Server{ReadHeaderTimeout` 等、リトライは `retry` / `backoff` |
| Node | `AbortSignal.timeout(`、axios / got / undici の `timeout:`、`setTimeout` でのレース、リトライは `retries` / `p-retry` |
| Python | `httpx` / `requests` の `timeout=`、`asyncio.wait_for(`、`urllib3.Retry` |
| 共通 | compose の `healthcheck.timeout`、nginx / ALB の `proxy_read_timeout` |

導出規則:

- **呼ばれる側の p99 目標 ≤ 呼び出し元タイムアウト ÷ 2**。半分にするのは、リトライや直列呼び出しの合計が呼び出し元の上限に収まるようにするため
- タイムアウトが入れ子なら外側から順に割る。例: 入口が 10s で待ち、内部 API が決済を 5s で待つなら、内部 API の p99 目標は 5s、決済の p99 目標は 2.5s が上限
- リトライがある呼び出しは、1 回あたりの上限 = タイムアウト ÷（リトライ回数 + 1）
- タイムアウトが見つからない呼び出しは「無制限」なので、**タイムアウトを足す提案** を別途添える（SLO より先に直すべき問題）

## 3. 役割別の初期値

| 役割 | 可用性（成功率） | p99 | 考え方 |
|---|---|---|---|
| `entry` | 99.9% | 1000 ms（API だけなら 500 ms） | 体感限界。内部サービスの合成なので最も緩くなる |
| `internal` | 99.95% | `min(1000 ms, 呼び出し元タイムアウト ÷ 2)` | 入口の 99.9% を支えるには内部は一段厳しく |
| `gateway` | 可用性は約束しない | 呼び出し元タイムアウト ÷ 2 | 外部起因の失敗は自分で減らせない。代わりに「結果不明（タイムアウト）」の件数を `--extra` で監視する |
| `worker` | RED は作らない | - | 不変条件のゲージ（`max(app.jobs.stale)` など）を 0 件で監視 |

可用性は「5xx 以外を成功」と数える。4xx は呼び出し側の問題として含めない。

## 4. しきい値への翻訳

実測は `verify-ingest.sh` の `baseline`（`requests_per_5m`、`error_rate_pct`、`p95_max_ms`）を使う。

- 許容エラー件数 / 5 分 = `requests_per_5m × (100 − 可用性) ÷ 100`
- `crit = max(ceil(許容エラー件数), 5)`、`warn = max(ceil(crit ÷ 2), 2)`。下限を置くのは、少ないトラフィックで 1 件のエラーに鳴らないため。**下限が効いたときは根拠にそう書く**（実質の SLO が緩くなっている）
- p99: `crit = 目標`、`warn = 目標 × 0.8`（50 ms 単位に丸める）

実測との照合:

- 実測 p95 × 1.5 が目標を超えていれば、提案時に示して「目標を緩める」か「先に性能を直す」かを聞く
- 実測が目標の 1/10 以下なら「緩い目標だが初期値として妥当」と添える（SLO は現状の性能ではなく約束）
- `window_minutes` が 30 分未満のベースラインは仮の値。「トラフィックが落ち着いたら再計算」を根拠に書く

## 5. 提示する表と 1 問

```
| サービス | 役割 | 可用性 | p99 目標 | 実測（件/5分, err%, p95） | 5xx warn/crit | p99 warn/crit | 根拠 |
|---|---|---|---|---|---|---|---|
| web | entry | 99.9% | 1000 ms | 3000, 0.1%, 120 ms | 2 / 5 | 800 / 1000 | 3000 × 0.1% = 3 件 → 下限 5 |
| api | internal | 99.95% | 2500 ms | 2900, 0.0%, 130 ms | 2 / 5 | 2000 / 2500 | web のタイムアウト 5s の半分 |
| pay | gateway | - | 2500 ms | 1000, 0.3%, 80 ms | 2 / 5 | 2000 / 2500 | api のタイムアウト 5s の半分。結果不明は --extra で監視 |
```

AskUserQuestion は 1 問: 「この目標で監視ルールを作ってよいですか？」
選択肢は「この通り」「全体を厳しく（可用性を一段上げ、p99 を 2/3 に）」「全体を緩く（可用性を一段下げ、p99 を 1.5 倍に）」。個別の修正は「その他」で受け、表を直して再提示せず、そのまま適用する。

## 6. 適用と再調整

承認した行を `create-monitors.sh --svc` に写す:

```bash
scripts/create-monitors.sh \
  --svc "web|err=2/5|p99=800/1000|slo=可用性 99.9% / p99 1000ms|note=3000 件/5分 × 0.1% = 3 件 → 下限 5" \
  --svc "api|err=2/5|p99=2000/2500|slo=可用性 99.95% / p99 2500ms|note=web のタイムアウト 5s の半分"
```

- `slo` と `note` は memo に書かれる。`|` は区切り文字なので note に使わない
- 後から変えるときは差分だけ渡す（`--svc "api|p99=1200/1500"`）。指定しなかったサービスと値は保たれる
- トラフィックが大きく変わったら `verify-ingest.sh` で `baseline` を取り直し、同じ式で件数を計算し直して再実行する
- ダッシュボードの参考線は監視ルールから読むので、`create-dashboard.sh` を再実行すれば追従する
